Attributes Reference

Configure entity auditing with PHP 8 attributes

Auditor uses PHP 8 attributes to configure Doctrine entity auditing. These attributes are defined in the damienharper/auditor core library and are shared across all providers.

📋 Overview​

AttributeTargetDescription
#[Auditable]ClassMarks an entity for auditing
#[Ignore]Property or classExcludes a property from auditing
#[Security]ClassDefines who can view entity audits
#[DiffLabel]Property or classAttaches a human-readable label resolver to a field
#[Mask]Property or classRecords the changes of a property without its values
#[AuditRoot]Class (repeatable)Indexes the entries under the history of another entity (see Histories)

📝 #[Auditable]​

Marks a Doctrine entity as auditable.

Namespace​

use DH\Auditor\Attribute\Auditable;

Usage​

<?php

use DH\Auditor\Attribute\Auditable;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[Auditable]
class Post
{
    // Entity will be audited
}

Parameters​

ParameterTypeDefaultDescription
enabledbooltrueWhether auditing is enabled
maxAge?stringnullRetention: entries older than this ISO 8601 duration are deleted by audit:clean
maxEntries?intnullRetention: only the N most recent entries are kept by audit:clean

Examples​

// Auditing enabled (default)
#[Auditable]
class Post {}

// Explicitly enabled
#[Auditable(enabled: true)]
class Post {}

// Disabled by default (can be enabled at runtime)
#[Auditable(enabled: false)]
class DraftPost {}

An entity disabled by default still gets an audit table, so that auditing can be enabled for it at runtime. If you never do that (e.g. a linter requires #[Auditable] on every entity and some are never meant to be audited), the skip_disabled_entities option leaves them without an audit table.

Retention Policy​

// Keep 7 years of history, whatever the global audit:clean cutoff
#[Auditable(maxAge: 'P7Y')]
class Payment {}

// Keep the 10,000 most recent entries (on top of the global audit:clean cutoff)
#[Auditable(maxEntries: 10_000)]
class Session {}

maxAge must be an ISO 8601 duration greater than zero and maxEntries a positive integer: invalid values fail when the entity metadata is loaded, with the entity name in the message. Both default to null (no policy). A policy given in the configuration (max_age / max_entries entity options) overrides the attribute value key by key.

Attribute values are cached with the ORM metadata: clear the cache after changing them. See audit:clean in the auditor documentation for how policies are applied.

Enabling/Disabling at Runtime​

$configuration = $provider->getConfiguration();

$configuration->disableAuditFor(Post::class);
$configuration->enableAuditFor(Post::class);

🚫 #[Ignore]​

Excludes a property from being tracked in audits.

Namespace​

use DH\Auditor\Attribute\Ignore;

Usage​

<?php

use DH\Auditor\Attribute\Auditable;
use DH\Auditor\Attribute\Ignore;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[Auditable]
class User
{
    #[ORM\Column(type: 'string')]
    private string $email = '';

    #[ORM\Column(type: 'string')]
    #[Ignore]  // Password changes won't be logged
    private string $password = '';

    #[ORM\Column(type: 'string', nullable: true)]
    #[Ignore]  // Tokens shouldn't be in audit logs
    private ?string $resetToken = null;
}

Parameters​

ParameterTypeRequiredDescription
field?stringOn the class onlyName of the ignored field; leave it out on a property

On the Class​

#[Ignore] can also be put on the class, once per field, with field naming the property. This is handy when the property is declared in a parent class or a trait you do not want to touch:

#[ORM\Entity]
#[Auditable]
#[Ignore(field: 'password')]
#[Ignore(field: 'resetToken')]
class User
{
    // ...
}

A class-level #[Ignore] without field, or a property-level one with field, throws an InvalidArgumentException when the attributes are loaded.

Combining with the Configuration​

  • The entity ignored_columns of the configuration are added to the #[Ignore] properties.
  • #[Ignore] wins over the audited_columns allowlist: a property marked with #[Ignore] is never audited, even when it is listed there.
  • To decide per object instead of per class, use the ignored_columns_resolver option (see Configuration).

Common Use Cases​

#[ORM\Entity]
#[Auditable]
class User
{
    // Security-sensitive fields
    #[Ignore]
    private string $password = '';

    #[Ignore]
    private ?string $salt = null;

    // Frequently changing but low-value fields
    #[Ignore]
    private int $loginCount = 0;

    #[Ignore]
    private ?\DateTimeInterface $lastActivityAt = null;
}

🔐 #[Security]​

Defines which roles are allowed to view audits for an entity.

Namespace​

use DH\Auditor\Attribute\Security;

Usage​

<?php

use DH\Auditor\Attribute\Auditable;
use DH\Auditor\Attribute\Security;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[Auditable]
#[Security(view: ['ROLE_ADMIN'])]
class User
{
    // Only users with ROLE_ADMIN can view User audits
}

Parameters​

ParameterTypeRequiredDescription
viewarray<string>YesArray of roles allowed to view audits

Examples​

// Single role
#[Security(view: ['ROLE_ADMIN'])]
class User {}

// Multiple roles (any of them grants access)
#[Security(view: ['ROLE_ADMIN', 'ROLE_AUDITOR', 'ROLE_COMPLIANCE'])]
class Order {}

How It Works​

The role checker callback is invoked when the Reader creates a query:

  1. Reader::createQuery() is called for an entity
  2. The role checker receives the entity class and 'view' scope
  3. If the role checker returns false, an AccessDeniedException is thrown
$configuration->setRoleChecker(function (string $entity, string $scope) use ($provider): bool {
    $entities = $provider->getConfiguration()->getEntities();

    if (!isset($entities[$entity]['roles'][$scope])) {
        return true;
    }

    foreach ($entities[$entity]['roles'][$scope] as $role) {
        if ($this->currentUserHasRole($role)) {
            return true;
        }
    }

    return false;
});

🏷️ #[DiffLabel]​

Without #[DiffLabel], a change from category 1 to category 2 stores:

{"categoryId": {"old": 1, "new": 2}}

With #[DiffLabel], the same change stores:

{"categoryId": {"old": {"value": 1, "label": "Books"}, "new": {"value": 2, "label": "Electronics"}}}

Labels are resolved at write-time and stored in the JSON — they remain accurate even if the referenced record is later renamed or deleted.

Namespace​

use DH\Auditor\Attribute\DiffLabel;

Usage​

<?php

use DH\Auditor\Attribute\Auditable;
use DH\Auditor\Attribute\DiffLabel;
use Doctrine\DBAL\Types\Types;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[Auditable]
class Product
{
    #[ORM\Column(type: Types::INTEGER)]
    #[DiffLabel(resolver: CategoryResolver::class)]
    private int $categoryId;
}

The resolver must implement DiffLabelResolverInterface. Return null to fall back to storing the plain scalar:

use DH\Auditor\Contract\DiffLabelResolverInterface;

final class CategoryResolver implements DiffLabelResolverInterface
{
    private const array LABELS = [1 => 'Books', 2 => 'Electronics', 3 => 'Clothing'];

    public function __invoke(mixed $value): ?string
    {
        return self::LABELS[$value] ?? null;
    }
}

Parameters​

ParameterTypeRequiredDescription
resolverstringYesFQCN of the DiffLabelResolverInterface implementation
field?stringOn the class onlyName of the field; leave it out on a property

As with #[Ignore], the attribute can be put on the class, once per field: #[DiffLabel(resolver: CategoryResolver::class, field: 'categoryId')]. A property-level #[DiffLabel] wins over a class-level one for the same field.

Wiring resolvers (standalone)​

Resolvers are looked up at flush-time via a PSR-11 ContainerInterface. Inject it on the provider before flushing:

use DH\Auditor\Provider\Doctrine\DoctrineProvider;
use Symfony\Component\DependencyInjection\ServiceLocator;

$provider = new DoctrineProvider($configuration);

$provider->setDiffLabelResolverLocator(new ServiceLocator([
    CategoryResolver::class => fn () => new CategoryResolver(),
]));

ServiceLocator comes from symfony/dependency-injection, which is not a dependency of the provider; any PSR-11 container keyed by the resolver FQCN works. When using the Symfony bundle, the locator is wired automatically — see the Diff Label Resolvers guide.

🎭 #[Mask]​

Records that a property changed without storing its values. Unlike #[Ignore], the change still shows in the history.

Namespace​

use DH\Auditor\Attribute\Mask;
use DH\Auditor\Masking\MaskStrategy;

Usage​

#[ORM\Entity]
#[Auditable]
class User
{
    #[ORM\Column(type: 'string')]
    #[Mask(strategy: MaskStrategy::KeyedHash)]  // HMAC-SHA256 of the email
    private string $email = '';

    #[ORM\Column(type: 'string', nullable: true)]
    #[Mask]                                     // "***"
    private ?string $pin = null;
}

Parameters​

ParameterTypeDefaultDescription
strategyMaskStrategyMaskStrategy::HiddenMaskStrategy::Hidden or MaskStrategy::KeyedHash
field?stringnullOn the class only: name of the masked field (repeatable)

Strategies​

  • MaskStrategy::Hidden stores "***" as old and new.
  • MaskStrategy::KeyedHash stores an HMAC-SHA256 of the value, keyed with the mask_secret option of the provider (at least 32 bytes, see Configuration). Equal values give equal hashes: the entries of one value can be found by hashing it with the same secret, without storing it. A string is hashed as is, any other value as its JSON encoding.

In both cases a null value stays null, and the values are compared before being masked: a change from "1234" to "5678" is recorded as "***" → "***". Masks apply to insert, update and, with full_snapshot_on_remove, remove entries, to columns and to-one associations (whose summary is masked). A masked field gets no #[DiffLabel] label, and a masked JSON field no deep diff.

An identifier (written in clear in object_id) and a collection (recorded by associate / dissociate entries) cannot be masked: a #[Mask] on either fails when the attributes are loaded, as does a MaskStrategy::KeyedHash without mask_secret.

WARNING

The label of an entity (its __toString() or the entity_label_resolver) is written in clear in the diffs: keep masked values out of it.

📄 Complete Example​

<?php

namespace App\Entity;

use DH\Auditor\Attribute\Auditable;
use DH\Auditor\Attribute\Ignore;
use DH\Auditor\Attribute\Security;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[ORM\Table(name: 'users')]
#[Auditable]
#[Security(view: ['ROLE_ADMIN', 'ROLE_USER_AUDITOR'])]
class User
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column(type: 'integer')]
    private ?int $id = null;

    #[ORM\Column(type: 'string', length: 180, unique: true)]
    private string $email = '';

    #[ORM\Column(type: 'string')]
    #[Ignore]  // Don't audit password changes (security)
    private string $password = '';

    #[ORM\Column(type: 'string', nullable: true)]
    #[Ignore]  // Don't audit reset tokens
    private ?string $resetToken = null;

    #[ORM\Column(type: 'integer')]
    #[Ignore]  // Frequent updates, low audit value
    private int $loginCount = 0;
}

🔀 Combining with Programmatic Configuration​

TIP

Attributes can be combined with or overridden by programmatic configuration.

use DH\Auditor\Provider\Doctrine\Configuration;

$configuration = new Configuration([
    'entities' => [
        // Override the Security attribute, scope by scope — more restrictive
        User::class => [
            'roles' => ['view' => ['ROLE_SUPER_ADMIN']],
        ],

        // Add additional ignored properties on top of attribute-defined ones
        Post::class => [
            'ignored_columns' => ['viewCount'],
        ],

        // Completely disable auditing despite #[Auditable]
        // (enabled: true cannot re-enable an #[Auditable(enabled: false)] entity)
        DraftPost::class => [
            'enabled' => false,
        ],
    ],
]);

✅ Best Practices​

  1. Always ignore sensitive data — Passwords, tokens, secrets, salts
  2. Use #[Security] for sensitive entities — Users, payments, orders, etc.
  3. Consider ignoring high-frequency low-value columns — last_activity_at, counters
  4. Apply the principle of least privilege — Start restrictive, relax as needed

WARNING

Never audit password fields or authentication tokens. Always use #[Ignore] on all security-sensitive properties.
