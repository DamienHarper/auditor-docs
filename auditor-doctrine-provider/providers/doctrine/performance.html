Version: 2.x

Performance

Cost of auditing a flush, and duration of the schema v2 migration

This page gives measured figures for the flush pipeline of the provider (audit entries built in onFlush and written before the COMMIT), comparing the latest 1.x release with 2.0, with and without batch INSERT, and the duration of audit:schema:migrate on a large schema v1 table. They come from one machine: use them as orders of magnitude and to compare configurations, and measure your own workload before relying on a precise figure.

📊 Summary​

  • 2.0 with batch_size: 0 (the default) costs about the same as 1.2.1: from 10 % faster to 2 % slower on SQLite, within ±3 % on PostgreSQL from 500 entities per flush. On MySQL, and with 50 entities per flush, the differences in either direction stay within the dispersion of the measurements.
  • 2.0 with batch_size: 500 writes the audit entries of a flush with multi-row INSERT statements. With 500 or 1,000 entities per flush, a flush is 10 to 18 % faster than with 1.2.1 on SQLite, 19 to 51 % faster on MySQL and 44 to 67 % faster on PostgreSQL. The more round trips cost (a remote database server, a network), the larger the gain.
  • Before the 2.0 release, fewer indexes, RETURNING id on PostgreSQL, a lighter transaction page, deferred joins for deep pages on MySQL and a batched audit:snapshot: see Before the 2.0 release.
  • Migrating a 1,000,000-row schema v1 audit table with audit:schema:migrate --force --convert-all took 5 minutes on MySQL and 3 minutes on PostgreSQL. See Schema v2 migration.

🚀 Before the 2.0 release: write, read and snapshot​

A last series of optimizations landed before the 2.0 release, each measured with the PHPBench suites of benchmarks/ (AuditBench, ReadBench, SnapshotBench), main before the changes against the branch, back to back on the same machine:

ChangeMeasured effect
3 secondary indexes fewer on audit tables (object_id, blame_id and discriminator alone)Flushes 20 to 28 % faster on PostgreSQL; indexes 30 % smaller on MySQL (raw INSERTs 18 % faster on a 300,000-row table)
INSERT … RETURNING id on PostgreSQL with batch_size: 0 (no SELECT LASTVAL() per entry)Included in the PostgreSQL figures above (raw INSERT: 152-178 → 82-87 µs per row)
Reader::getAuditsByTransactionId() introspects each audit table only, not the whole databaseTransaction page 89 to 99 % faster (200 unrelated tables)
Deep pages of an unfiltered query read with a deferred join on MySQL and MariaDBPage 500 of 1,000: 55 → 4 ms on MySQL
audit:snapshot writes multi-row INSERTs and loads the association targets of a batch togetherSnapshot 40 % faster on SQLite, 73 % on MySQL, 79 % on PostgreSQL
extra_data_provider called once per flush; driver, storage mapper and association metadata resolved onceWithin the dispersion of the flush figures

Method​

  • Machine: cloud container (Linux), PHP 8.5.13 CLI without Xdebug, MySQL 8.4 and PostgreSQL 17 (official Docker images, default configuration, reached on 127.0.0.1), SQLite in memory.
  • Flush (AuditBench): BENCH_N=500 entities per flush, BENCH_SEED_ROWS=20000 rows already in the audit tables, batch_size: 0; 5 iterations (10 for the SQLite re-run reported below).
  • Read (ReadBench): BENCH_READ_ROWS=50000 rows in post_audit, 200 unrelated tables in the database; 5 iterations of 5 revolutions after a warm-up.
  • Snapshot (SnapshotBench): 2,000 posts of 200 authors, default batch size (500); 5 iterations.
  • Reported: the mode in milliseconds, its rstdev, and the change. Results within ±10 % with an rstdev of the same order are noise.

🧪 Flush benchmarks​

Method​

The benchmark is benchmarks/AuditBench.php (PHPBench). Each scenario changes N entities of the test fixtures (Author, Post, Tag), all audited, and measures the single flush() that writes them — the Doctrine work and the auditing (changesets, diffs, audit rows). The schema is rebuilt and the data seeded before each iteration, outside the measured time.

ScenarioMeasured flushAudit rows
insertinsert N authorsN
updateupdate 3 fields of N postsN
removeremove N authorsN
associateadd a tag to N posts (many-to-many)2N
dissociateremove that tag from N posts2N
mixedinsert N/2 authors, update N/4 of the existing ones (2 fields), remove N/4N

Three configurations were measured back to back, for each database and each N:

ConfigurationCode
1.2.1tag 1.2.1 (latest 1.x release), schema v1
2.0-dev, batch_size: 0main at 169793e (batch INSERT), schema v2, one INSERT per entry¹
2.0-dev, batch_size: 500the same code with batch_size: 500

¹ The PostgreSQL N = 50 triplet was run again on main at ae51e10, which only changes audit:schema:migrate (see Reading the results). The first MySQL N = 1,000 triplet was discarded and run again: a dependency installation was running on the machine at the same time.

1.2.1 has no benchmark: benchmarks/AuditBench.php and phpbench.json of main were copied into a checkout of the 1.2.1 tag, with one change — the batch_size option was removed from the provider configuration, since 1.2.1 does not have it (its configuration rejects unknown options). The scenarios, fixtures and data are the same.

Settings: N = 50, 500 and 1,000; 10 iterations of 1 revolution, no warm-up; the reported value is the mode of the 10 iterations (PHPBench's kernel density estimate), with its relative standard deviation (rstdev).

Environment​

ItemValue
MachineApple M3 (8 cores), 16 GiB RAM, macOS 27.3
PHP8.5.12 (CLI, NTS), Xdebug not loaded and XDEBUG_MODE=off, OPcache disabled for the CLI
Librariesdoctrine/dbal 4.6.0, doctrine/orm 3.8.0, phpbench 1.7.0; damienharper/auditor 4.3.1 (1.2.1) and master at aca4003 (2.0-dev)
SQLitefile database on the local SSD (pdo-sqlite)
MySQL8.0.46 (mysql:8.0 image, default configuration), pdo-mysql

ContainersOrbStack (8 CPUs, 9.8 GiB), data on Docker volumes (on disk, no tmpfs), reached on 127.0.0.1

Reproduce​

Start the databases (any MySQL 8 / PostgreSQL 15 server will do; the benchmark empties the database it is given):

docker run -d --name bench-mysql -e MYSQL_ROOT_PASSWORD=password -e MYSQL_DATABASE=bench -e MYSQL_USER=auditor -e MYSQL_PASSWORD=password -p 33377:3306 mysql:8.0
docker run -d --name bench-pgsql -e POSTGRES_PASSWORD=password -e POSTGRES_DB=bench -p 54377:5432 postgres:15

Run a configuration (here 2.0 with batch_size: 500, 1,000 entities, PostgreSQL):

BENCH_N=1000 BENCH_BATCH_SIZE=500 BENCH_DATABASE_URL='pdo-pgsql://postgres:password@127.0.0.1:54377/bench?serverVersion=15' XDEBUG_MODE=off vendor/bin/phpbench run benchmarks/AuditBench.php --iterations=10 --revs=1 --report=aggregate
  • BENCH_DATABASE_URL takes a DBAL URL. Use the pdo-mysql://, pdo-pgsql:// and pdo-sqlite:/// schemes: with pgsql://, DBAL picks the native pgsql driver. For SQLite on disk, give an absolute path after the third slash (pdo-sqlite:////path/to/bench.sqlite); without BENCH_DATABASE_URL, the benchmark uses in-memory SQLite.
  • BENCH_BATCH_SIZE defaults to 0; it is ignored by the 1.2.1 copy of the benchmark.
  • Run the configurations you compare back to back, with the same N, and nothing else running on the machine.

Reading the results​

  • Dispersion. On SQLite and PostgreSQL, most rstdev values stay below 5 %: differences above 5 % are meaningful. MySQL (through the container's virtualized disk) is much noisier, with rstdev up to 51 %: there, only the large gains of batch_size: 500 are significant, and the ±20 % differences between 1.2.1 and batch_size: 0 are not. At N = 50, a flush lasts a few dozen milliseconds and the rstdev reaches 10 to 25 % on PostgreSQL too: the first run of the PostgreSQL N = 50 triplet gave the insert scenario 27.8 ms with 1.2.1 and 47.2 ms with batch_size: 0 (+70 %); run again, the three configurations back to back, it gave 43.3 ms and 38.1 ms (−12 %). The second run is the one reported above: at N = 50, read only the large differences.
  • batch_size: 0. Each audit entry is written with its own INSERT, as in 1.2.1: the schema v2 changes (JSON blame, ULID transaction_id, diffs envelope) do not make a flush measurably slower.
  • batch_size: 500. The gain grows with N and with the cost of a round trip: modest on SQLite (no network, 10 to 18 %), large on PostgreSQL (half of the time or less from N = 500). associate and dissociate, which write two audit rows per changed entity, gain the most. With N = 50, a flush writes 50 to 100 rows, a single multi-row statement: the gain is already visible but within a noisier range.

🗄️ Schema v2 migration​

The migration of a schema v1 audit table (see Upgrading to 2.0) was timed on a table of 1,000,000 rows written by 1.2.1, with audit:schema:migrate --force --convert-all (2.0-dev, main at e081182), on the machine and database servers described above.

Method​

  • Data: author_audit, generated with 1.2.1 (not measured) by cycles of three flushes, each in its own transaction: insert 20 authors, update them (2 fields), remove 10 of them. That is 50 audit rows and 3 transactions per cycle, i.e. 60,000 transactions for 1,000,000 rows (547 MiB on MySQL, 447 MiB on PostgreSQL).
  • Run: one database after the other, nothing else running; the command output is timestamped to get the duration of each step.

Results​

StepMySQL 8.0PostgreSQL 15
Additive DDL (new columns, schema_version, blame)50 s43 s
transaction_hash → transaction_id (60,000 ULIDs)100 s29 s
Diffs conversion (1,000,000 rows)139 s118 s
Legacy columns dropped< 1 s< 1 s
Total4 min 59 s3 min 13 s
Table size after OPTIMIZE TABLE / VACUUM FULL690 MiB (+26 %)614 MiB (+37 %)

After the migration, both tables had 60,000 distinct transaction_id values (one per legacy transaction, the grouping is kept), no row without transaction_id, blame or source in its diffs, and every row at schema_version 2.

  • What takes the time: every row is read, its diffs decoded, rewritten in the v2 envelope and updated. Both conversions work in batches of 500 rows (or transactions), each written in one database transaction, and read the rows through the primary key or the transaction_hash index: their duration grows linearly with the size of the audit tables.
  • Disk space: the rows are rewritten in place, so the table grows during the migration (878 MiB on MySQL and up to 1,783 MiB on PostgreSQL right after it, dead rows included) until InnoDB or autovacuum reuses the space, or until an OPTIMIZE TABLE / VACUUM FULL reclaims it. On PostgreSQL, the table reached up to 4 times its initial size: check the free disk space before migrating.
  • Your own estimate: --limit=N converts only N transactions or rows and keeps the legacy columns, so that a later run resumes where it stopped. Time a run on a sample and extrapolate linearly; test on a copy of your production data, with a backup, before the real migration.

Reproduce​

The scripts are not part of the repository; the steps are:

  1. With a checkout of the 1.2.1 tag, create the audit schema and write the v1 audit rows (any audited entity and workload will do; the larger the table, the more representative the figures).
  2. With 2.0, register the same entities and run the command, timing it:
time bin/console audit:schema:migrate --force --convert-all
